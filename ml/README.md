# ML-модуль «Умного кредитного кабинета»

Каталог ml содержит серверную часть проекта на FastAPI с двумя моделями: скоринговой моделью кредитного риска и моделью склонности лица, принимающего решение. Модуль работает как отдельный сервис, подключается к кредитному конвейеру по REST и не изменяет его бизнес-логику. Модели могут быть заменены на банковские без изменения контракта.

Документ последовательно описывает задачу, данные, обучение и результат. Описание модулей находится в personal_predlozhenie/README.md и predlozhenie_LPR/README.md, разбор открытого датасета Kaggle в kaggle_integration.md.

## Задача

Кредитному конвейеру малого и микро-бизнеса требуются два независимых решения.

Кредитное решение определяет вероятность дефолта и условия кредита. Пороговые правила не позволяют корректно оценить риск по множеству связанных признаков и объяснить клиенту размер ставки. Поэтому используется модель CatBoost: она прогнозирует вероятность дефолта, которая переводится в риск-грейд A/B/C/D, а итоговое решение формируют правила: запреты, возраст бизнеса, долговая нагрузка PTI, лимиты продуктов. Основной принцип: скоринг не является решением. При действующем запрете, например ограничении приставов, выдача отменяется независимо от оценки модели.

Коммуникационное решение определяет, в каком виде показать результат конкретному человеку. В малом бизнесе заявку подаёт один сотрудник, а решение принимает другое лицо: владелец, финансовый директор, главный бухгалтер или управляющий. Это ЛПР, лица, принимающие решение. Каждой роли требуется один и тот же кредит в разном виде: владельцу нужны сумма, срок и скорость, финансисту ставка, график и нагрузка, бухгалтеру комплект документов. Задачу решает модель склонности в модуле predlozhenie_LPR: она оценивает вероятность принятия предложения для каждой комбинации роли и формата и выбирает формат с максимальной оценкой.

## Данные

Банковские данные недоступны, поэтому используются синтетические данные с известной правдой. Методику можно воспроизвести на данных банка командой python train.py.

Дополнительно методика проверена на открытом датасете Kaggle MSME Credit Data by 30S-CR: 1707 малых и средних предприятий, 87 реестровых признаков, целевой признак: факт дефолта. На нём обучена вторая скоринговая модель CatBoost с метриками AUC 0.797 и KS 0.512. Описание признаков и подготовки данных находится в kaggle_integration.md.

На демонстрационном стенде часть внешних данных, в первую очередь БКИ, заменена заглушками, структура источников при этом сохранена. Каждая строка датасета содержит целевой признак, факт дефолта, рассчитанный по скрытой риск-функции от тех же признаков. Это обеспечивает разделимость классов и корректность метрик.

Данные для модели склонности формирует predlozhenie_LPR/lpr_data.py, около 12 000 взаимодействий. Одна строка соответствует одному показу предложения формата F человеку роли R. Модель использует три группы признаков: параметры сделки, роль ЛПР и формат подачи, история взаимодействий. Целевой признак: факт принятия предложения.

## Обучение

Все модели обучаются одной командой из каталога ml:

```bash
python train.py        # пять шагов, шаг 3 обучает модель на реальных данных, seed задаётся переменной ML_SEED
```

Скоринг построен по схеме, принятой для банковских моделей:

- разделение по времени: последние 20 процентов месяцев образуют тестовую выборку;
- CatBoost с лицензией Apache-2.0 и категориальными признаками: организационная форма, отрасль, цель; ручное кодирование не используется;
- калибровка вероятностей изотонической регрессией на отдельном временном интервале; вероятность дефолта 5 процентов означает, что пять из ста сопоставимых заёмщиков не вернут кредит;
- метрики тестовой выборки: AUC 0.77, KS 0.42, PSI 0.01; значения хранятся в artifacts/scoring_meta.json и доступны через GET /metrics;
- объяснимость: вклады SHAP по каждой заявке, топ 5 факторов с формулировками для сотрудника банка и клиента.

Модель на реальных данных обучается на шаге 3 из 5. Признаки: реестровые счётчики по временным окнам, капиталы в шкале log2, категориальные признаки без кодирования. Границы риск-грейдов рассчитаны по квантилям распределения вероятности дефолта. Для сравнения воспроизведена архитектура ResMLP из лучшего открытого решения на PyTorch. Точность accuracy 0.939 этой сети не отражает качество: доля предсказанных дефолтов равна нулю, класс дефолтов не распознаётся. Собственные метрики модели: AUC 0.797 и KS 0.512.

Модель склонности обучается по той же схеме: разделение по времени, CatBoost, метрики AUC 0.69 и KS 0.30 в artifacts/lpr_meta.json. Значения ниже, чем в скоринге, что ожидаемо для поведенческих данных. Для каждой заявки модель оценивает вероятность принятия по четырём форматам и выбирает максимальный; оценки по всем форматам возвращаются в поле alternatives.

При отсутствии артефактов скоринг переходит на эвристику rules.fallback_grade по БКИ, просрочкам, PTI и возрасту бизнеса, модуль ЛПР переходит на ранжирование по матрице приоров roles.py с признаком generated_by = prior.

## Результат

Сервис предоставляет REST-контракт, который оркестратор на Spring и Vaadin вызывает на каждом этапе конвейера. Для каждого этапа предусмотрен отдельный эндпоинт и сквозной /pipeline:

| Эндпоинт | Результат |
|---|---|
| POST /score | вероятность дефолта, риск-грейд, флаг запрета, топ-факторы SHAP |
| POST /decision | итоговый исход: одобрение, встречное предложение или отказ, с условиями, причинами и машинными кодами отказов |
| POST /banner | персональный баннер: offer, info при запрете, educational |
| POST /banner/html | тот же баннер в вёрстке «Альфа-Бизнес Онлайн»: три карточки, одна персональная и две классические, готовый HTML для вставки на страницу |
| GET /preview/banner | страница предпросмотра на демо-профиле, параметры scenario и role |
| POST /lpr | предложение под роль ЛПР: формат, заголовок, тело, акценты, канал, время контакта, склонность и сравнение вариантов |
| POST /pipeline | полный цикл: скоринг, решение, баннер, карточка ЛПР |
| POST /predict | ответ для фронтенда alfa-credit-cabinet: код баннера, уверенность, сумма, срок, причины. Без текстов, они живут в каталоге фронтенда |
| POST /msme/score | скоринг реальной компании по 87 реестровым признакам Kaggle-моделью: вероятность дефолта, грейд, факторы SHAP |
| POST /msme/offer | предложение для МСП: профиль, скоринг, решение, баннер, роль ЛПР |
| GET /metrics, GET /health | метрики всех моделей, включая реальную и сравнение с ResMLP, и доступность моделей для fallback-логики оркестратора |

Демонстрационный прогон smoke_test.py охватывает девять профилей и четыре роли ЛПР. Один из сценариев показывает приоритет запрета над моделью: при самозапрете выдача отклоняется. Один и тот же одобренный кредит формируется в четыре карточки: короткую, расчётную, документную и под задачу.

## Показ баннеров

На экране бизнеса отображаются три баннера. Один персонализированный и два классических. Классические карточки это рекламный ряд продуктовой линейки: кредит на оборотные средства и кредитная линия. В них указаны сумма, ставка и срок, от клиента они не зависят. Персональная карточка собирается в три шага: нужда из данных, отрасль, роль ЛПР.

Правило показа:

```
Экран бизнеса, три баннера:
    баннер 1, персонализированный, формируется под роль ЛПР
    баннер 2, классический, продуктовая подсказка
    баннер 3, классический, продуктовая подсказка

Для каждого баннера учитывается число показов без реакции:
    от 1 до 4 показов, баннер остаётся
    более 4 показов, баннер скрывается
    при клике счётчик показов обнуляется
```

| Показы без реакции | Действие |
|---|---|
| от 1 до 4 | Баннер остаётся |
| более 4 | Баннер скрывается |
| клик | Счётчик обнуляется, персональный баннер ведёт к заявке |

Правило ограничивает частоту показов: после четвёртого показа без реакции баннер скрывается. Это правило витрины. В модели склонности аналогичный эффект учтён в признаке числа предыдущих показов: с ростом числа показов вероятность принятия снижается. Сокращение числа нерелевантных показов повышает конверсию.

Готовая вёрстка карточек находится в personal_predlozhenie/banner_html.py. Геометрия и типографика повторяют раздел специальных предложений личного кабинета: карточка 294 на 208 пикселей, радиус 16 пикселей, заголовок 16 на 20 полужирным, описание 14 на 20, иллюстрация выходит за правый нижний угол. Цвета тем взяты из вёрстки банка: аметист, салат и зелёный. Имя клиента в баннер не выводится, поскольку обращение по имени в кредитном баннере воспринимается как вторжение в личное пространство. Заголовок строится от задачи, которую решает кредит: закрыть кассовый разрыв, закрыть налоговый долг, пополнить оборот на росте, взять технику в лизинг, закупить товар. Вторая строка содержит только сумму, ставку и срок. Платёж, переплата и служебные формулировки в карточку не выводятся. Страница предпросмотра доступна по адресу /preview/banner и позволяет сверить внешний вид без интеграции с фронтендом.

### Как собирается персональное предложение

Каталог предложений лежит в personal_predlozhenie/offers.py. Персональная карточка собирается от цели, и каждая цель опирается на своё поле заявки.

| Приоритет | Цель | Поле заявки | Заголовок карточки |
|---|---|---|---|
| 1 | цель назвал сам клиент | loan_purpose, preferred_product | Взять тягач в лизинг, Купить медоборудование |
| 2 | кассовый разрыв | cash_gap_flag | Закрыть кассовый разрыв |
| 3 | налоговый долг | tax_debt | Закрыть налоговый долг |
| 4 | нагрузка по кредитам | active_loans, existing_monthly_debt | Снизить платёж по долгам |
| 5 | рост оборота | turnover_trend_3m_pct | Пополнить оборот на росте |
| 6 | роль и отрасль | lpr_role, sector | Закупить товар к сезону, Открыть кредитную линию |

Цели налогового долга и роста оборота появились вместе с двумя полями заявки: tax_debt и turnover_trend_3m_pct. Оба поля приходят из выписки по счёту и из кабинета ФНС, оба проброшены в контракт фронтенда. В синтетике налоговый долг есть у 4 процентов заёмщиков, рост оборота выше 5 процентов у 35 процентов.

Порядок целей это и есть политика: цель, названная клиентом, сильнее любой догадки, а подтверждённая нужда сильнее роли. Поэтому при кассовом разрыве овердрафт получают все четыре роли, а в спокойном профиле карточки расходятся: владелец видит оборот, финдиректор кредитную линию, главбух кассовую дисциплину.

Соответствие отрасли и продуктов:

| Отрасль | Первый продукт | Далее |
|---|---|---|
| Розничная торговля | оборотный кредит | кредитная линия, овердрафт |
| Общепит | оборотный кредит | овердрафт, инвестиционный кредит |
| Производство | инвестиционный кредит | лизинг, оборотный кредит |
| Грузоперевозки | лизинг | оборотный кредит, овердрафт |
| Строительство | лизинг | кредитная линия, оборотный кредит |
| IT и услуги | оборотный кредит | кредитная линия, инвестиционный кредит |
| Медицина | инвестиционный кредит | лизинг, оборотный кредит |
| Сельское хозяйство | овердрафт | лизинг, оборотный кредит |
| Красота и сервис | оборотный кредит | овердрафт, инвестиционный кредит |

Продукт, который не подтверждается данными, не показывается. Овердрафт доступен только при кассовом разрыве, рефинансирование только при действующих кредитах. Лизинг и оборудование показываются только при подтверждении: цель в заявке или выбранный клиентом продукт. Одна отрасль подтверждением не считается, поэтому перевозчик без заявки на технику получит оборотный кредит, а не лизинг. Залог тоже не считается подтверждением цели. Если не проходит ни один продукт или банк отказывает по риску, персональная карточка заменяется информационной или обучающей, а классический ряд остаётся.

Сумма в карточке это доступный лимит, а не запрошенная сумма: платёж по нему не превышает допустимую долговую нагрузку грейда. Ставка складывается из ключевой, спреда грейда и спреда продукта. Если продукт карточки совпадает с продуктом кредитного решения, карточка берёт условия решения, чтобы числа на одном экране не расходились. Если продукт другой, карточка считает свои условия, а рядом остаются условия решения с кодом продукта: баннер предлагает лизинг, а решение в кабинете выдано по инвестиционному кредиту.

## Совместимость с фронтендом alfa-credit-cabinet

Фронтенд команды описан в репозитории alfa-credit-cabinet. Его контракт на модель лежит в docs/ML_BANNER.md: фронтенд присылает признаки клиента и ждёт только код баннера, потому что тексты, суммы и кнопки берёт из своего каталога. Наш сервис закрывает этот контракт адресом POST /predict, код в app/frontend_contract.py.

Запрос:

```json
{
  "client_id": "c-romashka",
  "features": {
    "company": {"legal_form": "OOO", "okved": "47.11", "region": "Москва", "age_months": 60, "employees": 24, "annual_revenue": 84000000},
    "turnover": {"months_of_history": 12, "avg_inflow_3m": 7400000, "trend_3m_pct": 12.5, "gap_months_12m": 0},
    "bki": {"has_history": true, "rating": 780, "active_loans": 1, "monthly_payments": 180000, "max_overdue_days": 0, "overdues_12m": 0, "requests_30d": 0},
    "tax_debt": 0,
    "industry_risk": "LOW",
    "debt_load": 0.02,
    "applications": {"has_draft": false, "draft_step": null, "recent_statuses": ["APPROVED"], "has_active_loan": true, "days_since_last_application": 1}
  }
}
```

Ответ:

```json
{
  "banner_code": "ACCEPT_OFFER",
  "score": 0.94,
  "model_version": "l2-catboost-1.0",
  "amount": null,
  "term_months": null,
  "reasons": ["По вашей заявке есть решение банка, оно действует ограниченное время"]
}
```

Как это работает внутри:

1. Признаки фронтенда переводятся в обычную заявку: возраст бизнеса в годах, оборот, отрасль по ОКВЭД, кредитная история, налоговый долг и тренд оборота. Налоговый долг и тренд идут только в выбор цели баннера, в модель они не попадают.
2. Скоринг считает вероятность дефолта, правила дают сумму и срок.
3. Код баннера выбирается по приоритетам каталога фронтенда, снизу вверх по таблице.
4. Если модель против оффера или заявка ещё в работе, сервис отвечает 204, и фронтенд не показывает баннер.

| Ситуация | Код баннера | Сумма и срок |
|---|---|---|
| заявка на подписании | SIGN_DOCS | из заявки |

Подключение занимает одну строку в public/config.js фронтенда:

```js
BANNER_MODEL_URL: 'http://localhost:8010/predict',
```

CORS в сервисе открыт, фронтенд ходит с другого порта. Таймаут у фронтенда 3 секунды, первый вызов может быть медленнее из-за загрузки модели.

## Структура и запуск

```
ml/
├── personal_predlozhenie/   # кредитная часть: признаки, скоринг, правила, баннеры
├── predlozhenie_LPR/        # подача под роль ЛПР: роли, синтетика, модель склонности, карточка
├── app/                     # FastAPI: маршруты и сборка ответа
├── data/                    # msme_kaggle.xlsx, открытый датасет
├── artifacts/               # обученные модели, метрики и демо-профили, готовы к запуску
├── train.py                 # обучение всех моделей, пять шагов
├── kaggle_integration.md    # разбор датасета Kaggle
├── smoke_test.py            # сквозной прогон без HTTP
├── Dockerfile, docker-compose.yml, run.ps1, run.sh
└── requirements.txt
```

Запуск: run.ps1 на Windows или run.sh на других платформах. В Docker:

```bash
docker compose up --build   # затем открыть http://localhost:8000/docs
```

В репозитории лежат модели, метрики и демо-профили, поэтому сервис поднимается сразу, без шага обучения. Тяжёлые результаты обучения, датасет синтетики, история взаимодействий ЛПР и веса референсной сети пересобираются командой python train.py, в репозиторий они не входят, состав артефактов описан в artifacts/README.md.

Модели обучаются на этапе сборки образа и детерминированы по seed, поэтому для запуска не требуются интернет и GPU. Параметры, включая ключевую ставку, объёмы синтетики и open-weight LLM для текстов баннеров, задаются переменными окружения, пример в .env.example.

Используемые библиотеки: CatBoost, scikit-learn, pandas, FastAPI. Все лицензии открытые, внешние веса в рантайме не загружаются.

Замечание: значение ML_KEY_RATE на дату защиты следует сверить с фактической ключевой ставкой, иначе ставки в предложениях будут выглядеть некорректно.
