# Умный кредитный кабинет предпринимателя — фронтенд

SPA на React 19 + TypeScript + Vite. Две зоны: **кабинет клиента** (предприниматель) и **рабочее место сотрудника банка**.
Бэкенд заявок в демо не нужен: все запросы перехватывает MSW, «сервер» живёт в `localStorage` и общий для вкладок браузера.
**Скоринг и персональный баннер считает настоящий ML-сервис** из каталога [`ml/`](ml/README.md) (FastAPI + CatBoost); без него фронт откатывается на встроенные заглушки.

## Запуск

```bash
npm ci
npm run dev        # http://localhost:5173
npm run build      # tsc -b + vite build
npm run lint
```

Моки включаются флагом `USE_MOCKS` в `public/config.js` (меняется без пересборки).

### Запуск вместе с ML-сервисом

```bash
# терминал 1: ML (порт 8000; модели уже лежат в ml/artifacts, обучать не нужно)
cd ml && ./run.sh            # Windows: .\run.ps1     |  Docker: docker compose up --build

# терминал 2: фронтенд
npm run dev                  # запросы /ml/* проксируются на http://127.0.0.1:8000
```

`public/config.js` → `ML_API_URL: '/ml'`. Другой адрес ML для dev-прокси: `ML_PROXY_TARGET=http://host:port npm run dev`.
Проверка, что сервис жив: `http://127.0.0.1:8000/health` (в ответе `model_available: true`).

| Что | Откуда | Если ML недоступен |
|---|---|---|
| Баннер на дашборде | ML `POST /predict` | правила-заглушка (`rules-stub-0.1`) |
| Скоринг заявки: PD, риск-грейд, факторы SHAP, условия одобрения / встречного, причины отказа | ML `POST /score` + `POST /decision` | локальный скоринг (`smb-score 2.4 (демо)`) |
| Авторизация, анкеты, статусы, подписание, ЕГРЮЛ / БКИ / ФНС, лента, очередь банка | по-прежнему MSW | — |

Модель на странице заявки видно по версии в карточке скоринга (сотрудник банка): `l2-catboost-…` — ML, `smb-score 2.4 (демо)` — заглушка.
Демо-заявки, которые создаются при первом запуске (история клиентов и очередь банка), считаются локальным скорингом; заявки, поданные вручную, — через ML.

## Демо-сценарии

| Логин | Роль | Сценарий |
|---|---|---|
| `romashka` | ООО, клиент | Идеальный заёмщик: обороты растут. Есть **одобренная** заявка → «Оформить» → подписание → выдача |
| `petrova` | ИП, клиент | Кассовые разрывы (сезонная выручка). **Встречное предложение**: «запрошено vs предложено» |
| `novikov` | ИП, клиент | Бизнесу 8 месяцев, кредитной истории нет. **Отказ** с советом + незаконченная анкета (автосохранение) |
| `ivanova` | Сотрудник банка | Очередь, карточка заявки, скоринг, консоль решения, audit-log |

Пароль у всех — `demo1234`. Сессия хранится в `sessionStorage`, поэтому клиент и сотрудник открываются **в соседних вкладках**:
клиент подаёт заявку → она за ~14 с проходит конвейер → сотрудник принимает решение → экран клиента обновляется сам.

Правило маршрутизации: заявки **до 1 000 000 ₽** с уверенной оценкой решаются автоматически, остальные уходят сотруднику.
Исход (одобрение / встречное / отказ) и условия определяет ML; при подключённом ML сценарии ниже зависят от его ответа и могут отличаться от описанных.
Сбросить данные к исходным — кнопка на странице входа.

## Архитектура (Feature-Sliced Design)

```
src/
  app/        провайдеры, роутер (lazy-маршруты по зонам), лэйауты, стили и токены
  pages/      client-home, application-new, application/{status,decision,signing}, bank-queue, bank-application
  widgets/    news-feed, application-pipeline, decision-outcome, scoring-report, enrichment-report, audit-log
  features/   auth, application-wizard, track-application, offer-response, sign-documents, bank-decision
  entities/   application (статусы, этапы конвейера, типы, API), product, feed, banner, user
  shared/     api-клиент, ui-кит, lib (форматирование, аннуитет, реквизиты, хуки), config, mocks
```

### Персональный баннер (ML)

Над сводкой на дашборде показывается баннер, который выбирает модель; клиент видит, **почему** (кнопка «Почему я это вижу»),
может скрыть его, а события показа/клика/закрытия уходят в журнал для дообучения.
Модель подключается через `ML_API_URL` в `public/config.js` (баннер берётся с `POST {ML_API_URL}/predict`; отдельный адрес — `BANNER_MODEL_URL`); без неё или при недоступности сервиса работает встроенная заглушка на правилах.
Контракт запроса/ответа, коды баннеров и OpenAPI-фрагмент — в [`docs/ML_BANNER.md`](docs/ML_BANNER.md).

### Маршруты

| Путь | Экран |
|---|---|
| `/` | Дашборд: сводка, заявки, продукты, персональная лента |
| `/applications/new` | Smart-анкета (мастер из 4 шагов). `?product=&amount=&term=` — подстановка из предложения |
| `/applications/:id` | Статус: этапы NEW → DATA_CHECK → ENRICHMENT → SCORING → DECISION |
| `/applications/:id/decision` | Решение: одобрение / встречное предложение / отказ |
| `/applications/:id/signing` | Мок подписания (код из SMS показывается на экране) и выдача |
| `/bank/queue` | Очередь с фильтрами (статус, риск, сумма, поиск) — фильтры в URL |
| `/bank/applications/:id` | Карточка: скоринг с объяснимостью, обогащение, анкета, консоль решения, audit-log |

### Состояние

- **Анкета** — `features/application-wizard`: Context + `useReducer`. Черновик хранится на сервере,
  автосохранение через 800 мс после изменения (с повтором при ошибке и досохранением при уходе со страницы),
  клиент продолжает с того же шага. Предзаполнение — из профиля компании, оборотов по счёту и кредитной истории.
- **Статус заявки** — `features/track-application`: один провайдер на все экраны `/applications/:id/*`.
  Интервал поллинга зависит от того, чей ход: система — 1,5 с, банк — 4 с, клиент — 10 с, финальный статус — стоп.
  Пауза в скрытой вкладке, экспоненциальная задержка при ошибках.
- Остальные экраны — `shared/lib/hooks/useRequest` (отмена через AbortController, перезапрос) и `useAutoReload`.

### Моки (`shared/mocks`)

- `fixtures/borrowers.ts` — 12 синтетических заёмщиков (ИНН/ОГРН проходят контрольные суммы).
- `engine/scoring.ts` — локальный объяснимый скоринг (запасной вариант, если ML недоступен): балл = 640 + вклад признаков, PD, класс риска,
  проверка посильности платежа → рекомендация «одобрить / встречное / отказ».
- `engine/mlScoring.ts` — адаптер к ML: анкета и данные «внешних источников» → `Application` ML → ответ `/score` + `/decision` → тот же `Scoring`, что рисует интерфейс.
- `engine/pipeline.ts` — машина состояний заявки по расписанию + audit-log каждого шага.
- `engine/feed.ts` — лента из состояния заявок и динамики оборотов.
- `db.ts` — хранилище в `localStorage`; каждый запрос продвигает конвейер до текущего момента.

Основные эндпоинты: `GET/POST/PUT/DELETE /applications/draft`, `POST /applications/draft/submit`,
`GET /applications/:id`, `POST /applications/:id/offer/{accept,decline}`, `POST /applications/:id/signing/{code,confirm}`,
`GET /client/{products,feed,banner}`, `POST /client/banner/events`, `GET /bank/applications`, `GET /bank/applications/:id`, `POST /bank/applications/:id/decision`.
